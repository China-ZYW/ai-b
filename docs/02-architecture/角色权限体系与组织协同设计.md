# AI 数据助理 · 角色权限体系与组织协同设计

> 本文档是《前后端架构设计文档》与《SaaS 多租户与数据源接入设计》的专项补充，聚焦四个能力：
> **① 四级主体（运营 / 组织租户 / 团队 / 个人）的角色权限体系**、**② 组织邀请与成员生命周期**、**③ 菜单与按钮级前端权限**、**④ API 级后端权限**。
> 落地形态仍为模块化单体（Spring Boot 3.2.5 + MyBatis-Plus 3.5.5 + Vue 3.5.11），元数据仍存 `aibi_meta`，行级隔离仍由 `TenantLineInnerInterceptor` 强制。代码骨架与落地映射见第 12 章，分阶段实施见第 13 章。

## 1. 背景与目标

### 1.1 现状盘点

| 维度 | 现状实现 | 代码位置 | 不足 |
| --- | --- | --- | --- |
| 认证 | 无状态 JWT（HS256），claims 含 `uid/tid/plan/role` | `common/security/JwtTokenProvider.java`、`JwtAuthFilter.java` | `role` 只有单值；无会话版本，改权限须等令牌过期 |
| 平台角色 | `app_user.role ∈ {SUPER_ADMIN, USER}`，超管 `tenant_id=0` | `common/security/UserContext.java` | 运营 / 审计 / 客服无法分权，超管一把钥匙 |
| 组织角色 | 无。租户内所有用户等价 | — | 无法区分组织管理员、数据管理员、分析师、只读 |
| 团队 | 无 | — | 无部门/项目组维度，资源只能"组织内全可见"或"仅自己" |
| 租户隔离 | `TenantLineInnerInterceptor` 自动注入 `tenant_id`，IGNORE 名单显式维护 | `common/config/MybatisPlusConfig.java` | 隔离到租户即止，租户内无第二层收敛 |
| API 门禁 | `/api/admin/**` → `hasRole("SUPER_ADMIN")`，其余 `authenticated()` | `common/security/SecurityConfig.java` | 粗粒度；业务接口只判"登录没登录"，不判"能不能做" |
| 前端门禁 | 路由 `meta.role='SUPER_ADMIN'` + `navItems` 数组硬编码 | `router/index.ts`、`components/layout/AppLayout.vue` | 菜单写死；无按钮级控制；新增页面须改两处 |
| 邀请 | 无。账号只能由超管在后台 `POST /api/admin/users` 建 | `module/admin/service/UserAdminService.java` | 组织无法自助扩张成员 |
| 席位 | 无。`tenant` 只有次数配额（`daily_limit/total_limit`） | `resources/db/metadata-schema.sql` | 无法按人数计费/限制 |
| 审计 | 无独立审计表（`query_history` 只记问数） | — | 权限变更、登录、邀请、越权拦截无留痕 |

### 1.2 目标

| 目标 | 要求 |
| --- | --- |
| 四级主体 | 平台运营（跨租户）→ 组织租户（计费与隔离边界）→ 团队（协作与归属边界）→ 个人（成员身份），职责与权限边界清晰、不越级 |
| 权限可配 | 权限点是**唯一事实源**：同一份 `permission` 字典同时驱动后端 API 门禁、前端菜单渲染、前端按钮显隐，杜绝"前后端各写一套" |
| 组织自助 | 组织管理员可自建团队、邀请成员、分配角色、管理席位，无需平台介入 |
| 邀请闭环 | 支持链接邀请 / 定向邀请（邮件短信）/ 批量导入 / 申请加入四通道，含有效期、席位上限、审批、撤销、防提权 |
| 即时生效 | 权限变更（尤其移除成员、停用、降级）**不依赖令牌自然过期**，敏感变更秒级吊销 |
| 兼容存量 | 老库启动即自动演进结构与回填数据（沿用 `SchemaMigration` + `DataSeeder` 幂等模式），不停机、不破坏已存指标 SQL |

### 1.3 Non-goals（本期不做）

- 不做 ABAC（属性基访问控制）/ 策略引擎（OPA、Casbin）——当前规模下 RBAC + 数据范围 + 资源 ACL 已足够，引入策略引擎会显著抬高运维与调试成本。
- 不做字段级/列级脱敏权限（列级数据权限归入 V2，与语义层 `semantic_meta` 联动）。
- 不做 SSO / OAuth2 / LDAP / 企业微信扫码（预留 `user_identity.auth_source` 扩展位，本期只做本地口令）。
- 不做租户内多套权限模板市场（自定义角色仅组织内私有）。
- 不改造业务库侧权限：平台连业务库始终用**只读账号**，业务库的行级权限不归平台管。

### 1.4 设计原则

1. **后端是唯一安全边界**。前端菜单/按钮隐藏只改善体验，任何权限判定必须在服务端重做；`v-perm` 被绕过不等于越权成功。
2. **权限点单一事实源**。菜单编码、按钮编码、API 权限码是同一个 `permission.code`，前端不下发"菜单树"而下发"权限码集合"，菜单树由前端路由表 + 权限码过滤生成（避免后端维护前端路由）。
3. **默认拒绝，显式放行（fail-closed）**。平台运营域与组织管理域接口未标注权限点即拒绝；问数域为兼容存量默认"仅需认证"，但由接口矩阵扫描页高亮未标注项，逐步收敛。
4. **DENY 优先**。自定义角色的 `DENY` 覆盖永远压过任何 `GRANT`，便于"给分析师角色但禁掉导出"。
5. **不可隐式提权**。团队角色不得授予组织级权限；授予者不能授出高于自身最高角色的角色；`OWNER`/`SUPER_ADMIN` 永不可被授予，只能转让。
6. **隔离不依赖开发自觉**。租户维度沿用 `TenantLineInnerInterceptor` 自动注入；团队维度沿用同一套拦截器机制追加数据范围条件，而不是每个 Service 手写 `if`。
7. **权限变更可追溯**。授权/回收/邀请/接受/移除/登录/越权拦截一律落 `auth_audit_log`，运营与组织管理员各自可查本域。

## 2. 四级主体模型

### 2.1 主体层级与边界

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ① 平台运营域  Platform（tenant_id = 0，跨租户）                            │
│    SUPER_ADMIN / OPERATOR / AUDITOR / SUPPORT                              │
│    边界：租户开通·续费·停用·席位配额、平台内容运营（手册/模板/主题/图表规则）、 │
│          大模型配置、权限字典维护、全平台审计。                                │
│    红线：不得读取租户业务数据明文、不得获取数据源凭证明文、不得代客改业务口径。    │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 开通 / 治理
                                ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ ② 组织租户  Organization = tenant（tenant_id，隔离与计费边界）               │
│    OWNER / ADMIN / DATA_STEWARD / ANALYST / VIEWER / BILLING               │
│    边界：成员与团队管理、数据源接入、语义层与指标口径、驾驶舱、分享、席位用量。   │
│    承载：现有全部 tenant_id 隔离表（data_source / query_history / metric …）  │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 划分
                                ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ ③ 团队  Team（team_id，协作与资源归属边界，支持 parent_id 树形）             │
│    TEAM_OWNER / TEAM_EDITOR / TEAM_VIEWER                                  │
│    边界：团队内资源可见性收敛、团队级邀请、团队级用量归集。                     │
│    约束：团队不是隔离边界（同租户内跨团队仍可能经 ACL 授权可见），              │
│          团队角色不携带任何组织级权限。                                        │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 归属（多对多）
                                ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ ④ 个人  Member = app_user（uid，组织内的成员身份）                          │
│    资源所有者（owner_uid）、数据范围终点（SELF）、审计主体                     │
└──────────────────────────────────────────────────────────────────────────┘
```

**三条边界的判定语义**（务必区分，否则会写错代码）：

| 边界 | 谁强制 | 违反后果 | 错误码 |
| --- | --- | --- | --- |
| 租户边界 | `TenantLineInnerInterceptor` 自动注入 `tenant_id`（框架级，不可绕过） | 跨租户数据不可见（查不到行），非报错 | — |
| 团队边界 | `DataScopeInterceptor` 追加 `(owner_uid=? OR team_id IN(...) OR visibility='TENANT')` | 越界查询返回空 / 写操作报错 | `40310` |
| 功能边界 | `@RequiresPermission` 切面 + Security URL 规则 | HTTP 403 | `40301` |

### 2.2 个人版 = 单人组织（模型统一，不开特例分支）

个人用户注册后，系统一次性创建：

```
user_identity(1)  ──▶  tenant(plan=FREE, seat_limit=3)  ──▶  team(code='default', name='我的空间')
                                     │                                   │
                                     └──▶ app_user(role=OWNER) ◀─────────┘
                                              team_member(TEAM_OWNER)
                                              user_role(TENANT/OWNER)
```

- 个人版与组织版走**同一套代码路径**，差异只在 `tenant.plan` 与 `seat_limit` 的默认值；FREE 也允许邀请至多 3 人（`seat_limit=3`），把"个人版"变成天然的增长入口。
- 默认团队 `code='default'` 不可删除、不可改 code；`tenant.default_team_id` 指向它。用户未显式选择团队时，上下文回落到默认团队。
- 存量单用户租户迁移时同样补建默认团队（见 §11.2），保证"团队层"对老数据也是全覆盖的，业务代码不必写 `teamId == null` 的兼容分支。

### 2.3 关键决策：多组织身份 = 账号身份 + 组织成员身份

一个人可能被 A、B 两个组织同时邀请。现有 `app_user.tenant_id` 是单值 + `username` 全局唯一，直接支持多组织会动到全局唯一约束与登录链路。两种方案：

| | 方案 A（**采纳**）：`user_identity` + 多个 `app_user` 身份 | 方案 B（否决）：`app_user` 升为全局用户 + `user_tenant` 多对多 |
| --- | --- | --- |
| 模型 | identity（自然人：邮箱/手机/口令/头像）1 ── n app_user（组织内成员身份，各自有 uid） | app_user（自然人）1 ── n user_tenant（成员关系） |
| `uid` 语义 | 组织内身份 id，**与现有全部 `uid` 列语义完全一致** | 变成全局 id，`query_history.uid`、`metric.uid`、`dashboard.uid`、`share_link.uid` 语义全部漂移 |
| 存量改造 | 只加一列 `app_user.identity_id` + 改登录流程 | 废弃 `app_user.tenant_id`、重签全部 `uid`、`username` 唯一约束下沉、IGNORE 名单重排 |
| 隔离风险 | 零：`tenant_id` 注入逻辑一行不改 | 高：`uid` 跨租户复用后，任何漏加 `tenant_id` 的 SQL 都可能串数据 |
| 计费审计 | 天然按身份归集，`uid` 即"该组织内的人" | 需额外维度区分"同一人在不同组织的用量" |
| 用户体验 | 登录后多组织时进入"选择组织"页；切换组织=换 JWT（`tid`+`uid` 同变） | 登录后选组织；切换组织=换 JWT（`tid` 变、`uid` 不变） |
| 代价 | 个人资料需在 identity 层统一维护（昵称/头像/口令），组织内可覆盖昵称 | — |

**采纳方案 A**。核心收益是"隔离与 `uid` 语义零风险"，代价（个人资料双层）用一个约定化解：

- **口令、头像、手机号、邮箱只在 `user_identity` 层维护**（改一次全组织生效）；
- **昵称、职位、可见性偏好可在 `app_user` 层覆盖**（`app_user.nickname` 非空则优先，为空回落 identity）。
- 切换组织 = `POST /api/auth/switch-identity` 重新签发 JWT，前端清空所有 store 后重载（不允许"半个上下文"残留，这是串数据的高发点）。

### 2.4 上下文传播：AccessContext

现有 `TenantContext`（`tenantId + plan`）与 `UserContext`（`uid + username + role`）合并升级为 `AccessContext`，**但保留两个旧类作为门面委托**，避免大范围改动现有代码（`TenantContext.tenantId()` / `UserContext.userId()` 调用点遍布各 Service）：

```java
/** 全链路访问上下文：由 JwtAuthFilter 写入、请求结束清理（沿用现有 ThreadLocal 生命周期）。 */
public record AccessContext(
        Long uid,                      // 组织内成员身份 id（app_user.id）
        Long identityId,               // 自然人 id（user_identity.id）
        String username,
        Long tenantId,
        String plan,
        Set<String> platformRoles,     // 平台角色（仅 tenant_id=0 身份非空）
        Set<String> orgRoles,          // 组织角色（OWNER/ADMIN/...）
        Long currentTeamId,            // 当前团队上下文（JWT claim: team）
        Set<Long> teamIds,             // 该身份所属全部团队（数据范围用）
        Set<Long> childTeamIds,        // currentTeamId 的全部子团队（TEAM_AND_CHILD 范围用）
        DataScope dataScope,           // 有效数据范围（多角色取最宽）
        long permVersion               // 权限版本（与库中比对，实现即时吊销）
) {
    public boolean isPlatform() { return tenantId != null && tenantId == 0L; }
    public boolean hasOrgRole(String code) { return orgRoles.contains(code); }
    public boolean isOwner() { return orgRoles.contains(OrgRole.OWNER); }
}
```

- `TenantContext.set/get/clear` 内部委托 `AccessContextHolder`，`getTenantId()` 返回 `ctx.tenantId()`——**现有代码零改动**。
- `UserContext.isSuperAdmin()` 改为 `ctx.platformRoles().contains("SUPER_ADMIN")`，保持方法签名不变。
- `childTeamIds` 在 `AccessContextBuilder` 构建时用一次 `WITH RECURSIVE`（MySQL 8）或内存树展开计算，随上下文缓存（Caffeine，key=`tenantId`，TTL 5min），避免每请求查树。
- 请求结束必须 `clear()`（现有 `JwtAuthFilter` 的 `finally` 已具备该结构，扩展即可），杜绝线程复用串上下文。

## 3. 角色体系（RBAC）

### 3.1 三层角色分层

| 层级 | 存储 | 生效范围 | 授予者 | 能否授予更高层级 |
| --- | --- | --- | --- | --- |
| 平台角色 `PLATFORM` | `user_role(scope_type='PLATFORM', scope_id=0)` | 跨租户（`tenant_id=0` 身份） | SUPER_ADMIN | 否 |
| 组织角色 `TENANT` | `user_role(scope_type='TENANT', scope_id=tenantId)` | 本租户全部团队 | OWNER / ADMIN | 否（团队角色可） |
| 团队角色 `TEAM` | `user_role(scope_type='TEAM', scope_id=teamId)` | 仅该团队（含子团队，取决于角色 `inherit_to_child`） | ADMIN / TEAM_OWNER | 否 |

**层间关系**：三层是**并集**而非覆盖。用户在组织内的有效权限 = 组织角色权限 ∪ 当前团队角色权限 ∪ 资源 ACL 授权 − DENY 覆盖。团队角色**永远不能**携带组织级权限点（由 `permission.level` 字段约束，授予时校验：`TEAM` 角色只能绑定 `level ∈ {TEAM, RESOURCE}` 的权限点）。

### 3.2 平台运营角色（运营用户）

| 角色码 | 名称 | 核心职责 | 明确禁止 |
| --- | --- | --- | --- |
| `SUPER_ADMIN` | 平台超级管理员 | 全权：权限字典维护、运营/审计/客服账号授予、租户全生命周期、大模型全局配置、平台默认配置、内容运营、审计全域 | — （唯一可授出平台角色的角色） |
| `OPERATOR` | 运营用户 | 租户开通/续费/停用/延期、席位与次数配额调整、内容运营（用户手册发布、驾驶舱模板、主题令牌、图表规则全局项）、邀请与审批治理、运营看板 | 不可改权限字典、不可授予平台角色、不可读数据源凭证、不可看审计日志正文中的 SQL 明文 |
| `AUDITOR` | 平台审计 | 只读全平台审计日志、登录记录、越权拦截记录、用量与配额、权限授予链路 | 全部写操作；不可读业务数据与凭证 |
| `SUPPORT` | 技术支持 | 只读诊断：租户状态、错误码统计、失败问数记录（脱敏）、大模型连通性；可发起**代客协助授权申请** | 未经租户 OWNER 同意不得进入租户工作台；不可改任何配置 |

> `SUPPORT` 的"代客协助"是运营域最敏感的入口，机制见 §9.3：申请 → 租户 OWNER 审批 → 签发**限时限权的影子令牌**（`scope=ASSIST`，只读，TTL ≤ 2h，全程审计 + 顶栏红色横幅提示"平台协助中"）→ 到期自动失效。

### 3.3 组织角色（租户内）

| 角色码 | 名称 | 数据范围 | 关键权限点（摘要，全量见 §4.1） |
| --- | --- | --- | --- |
| `OWNER` | 组织所有者 | ALL | 全部组织权限点 + `org:org:transfer`（转让）+ `org:org:dissolve`（解散）+ `member:role:assign` 无限制 |
| `ADMIN` | 组织管理员 | ALL | 成员/团队/邀请/角色分配（不可授出 OWNER）、数据源全部、调优全部、配额查看、组织设置（不可转让/解散） |
| `DATA_STEWARD` | 数据管理员 | ALL | 数据源 CRUD 与连通测试、语义层、样例库、图表规则、结果展示配置、主题；**不含**成员管理 |
| `ANALYST` | 分析师 | TEAM_AND_CHILD | 问数、指标 CRUD、驾驶舱 CRUD、分享、收藏、历史（本人+团队）；数据源只读、调优只读 |
| `VIEWER` | 只读成员 | TEAM | 问数（可被组织设置关闭 `org:allow_viewer_query`）、查看被授权指标/驾驶舱、查看历史（仅本人）；**不可**导出、不可分享、不可建指标 |
| `BILLING` | 计费联系人 | TENANT（仅用量域） | 用量与账单只读、续订入口、席位查看；无业务数据权限 |

角色继承约定：`OWNER ⊃ ADMIN ⊃ DATA_STEWARD ∪ ANALYST ⊃ VIEWER`（逻辑包含关系，但实现上**不做隐式继承**，而是每个内置角色显式列出全部权限点——隐式继承会让"给 VIEWER 加一个权限"变成改代码）。

### 3.4 团队角色

| 角色码 | 名称 | 数据范围 | 权限 |
| --- | --- | --- | --- |
| `TEAM_OWNER` | 团队负责人 | TEAM_AND_CHILD | 团队内成员增删与角色分配（限团队角色）、团队资源全部、团队级邀请（`seats` 受组织席位余量约束）、团队设置 |
| `TEAM_EDITOR` | 团队编辑者 | TEAM_AND_CHILD | 团队内指标/驾驶舱/收藏/分享 CRUD、问数、团队资源读 |
| `TEAM_VIEWER` | 团队只读 | TEAM | 团队资源只读、问数（同 VIEWER 约束） |

`role.inherit_to_child=1` 时，团队角色对 `parent_id` 链上的全部子团队生效（`childTeamIds`）。默认 `TEAM_OWNER`/`TEAM_EDITOR` 继承、`TEAM_VIEWER` 不继承。

### 3.5 自定义角色与权限增减

组织可基于内置角色派生自定义角色（`custom_role`），并用 `role_permission_override` 做**增减**：

```
自定义角色「分析师-禁导出」
  base_role_code = 'ANALYST'
  data_scope     = 'TEAM_AND_CHILD'
  overrides      = [ {code:'chat:query:export', effect:'DENY'},
                     {code:'share:link:write',   effect:'DENY'} ]

有效权限 = perm(ANALYST) − {chat:query:export, share:link:write}
```

约束（服务端强校验，不可由前端保证）：

1. `DENY` 永远优先于 `GRANT`，且 `DENY` 不可被 `base` 角色的任何 `GRANT` 反转。
2. 自定义角色只能增减 `level ∈ {TENANT, TEAM, RESOURCE}` 的权限点，**不可**含平台权限点。
3. 自定义角色不可包含 `org:org:transfer`、`org:org:dissolve`、`member:role:assign`（后者可单独授予，但不进自定义角色，避免"自建角色自我提权"）。
4. 自定义角色数量受套餐约束（FREE=0、PRO=5、ENTERPRISE=不限），落 `sys_config` 可调。
5. 删除自定义角色前校验在用人数，>0 时要求先迁移（返回 `40002` 与在用清单）。

### 3.6 有效角色与权限的合并算法

```
输入：uid, tenantId, currentTeamId
输出：Set<String> permissions, DataScope dataScope

① 取平台角色：platformRoles = user_role(uid, scope=PLATFORM)
   —— 仅当 tenantId == 0 时参与计算；非 0 时强制为空集
      （防止"超管身份"被带进租户上下文形成跨域提权）

② 取组织角色：orgRoles = user_role(uid, scope=TENANT, scope_id=tenantId)
              ∪ custom_role 展开（base_role_code 的权限 + overrides）

③ 取团队角色：teamRoles = user_role(uid, scope=TEAM, scope_id ∈ {currentTeamId} ∪ ancestorChain)
   —— 只取"当前团队及其祖先链上声明 inherit_to_child=1"的角色

④ 权限并集：P = ∪ perm(role) for role in (platformRoles ∪ orgRoles ∪ teamRoles)

⑤ DENY 收敛：P = P − { code | override(code, DENY) 命中该 uid 的任一角色 }

⑥ ACL 附加：P_acl = resource_acl 中 principal ∈ {USER:uid, TEAM:teamIds, ROLE:orgRoles}
                     的授权（作用于具体资源，不进 P，在资源判定时单独查）

⑦ 数据范围：dataScope = widest( role.data_scope for role in orgRoles ∪ teamRoles )
   宽窄序：ALL > TENANT > TEAM_AND_CHILD > TEAM > SELF
   —— 取最宽（不是最窄）：兼任 ADMIN 与 TEAM_VIEWER 的人应按 ADMIN 看全域

⑧ 套餐裁剪：P = P ∩ planAllowed(plan)
   —— 例：FREE 不含 org:seat:buy / dashboard:screen:publish（大屏公开发布）
```

**缓存键**：`perm:{tenantId}:{uid}:{teamId}` → `PermissionSet`；`role:{roleCode}` → `perm(role)`；两级 Caffeine 缓存，TTL 5min，配合 `perm_version` 主动失效（§6.3）。

**防提权校验（授予侧，独立于合并算法）**：

```java
void assertCanGrant(AccessContext grantor, String targetRoleCode, String scopeType) {
    if ("PLATFORM".equals(scopeType) && !grantor.platformRoles().contains("SUPER_ADMIN"))
        throw new BizException(FORBIDDEN, "仅平台超级管理员可授予平台角色");
    if (OrgRole.OWNER.equals(targetRoleCode) || "SUPER_ADMIN".equals(targetRoleCode))
        throw new BizException(FORBIDDEN, "该角色不可被授予，请使用转让流程");
    Role target = roleService.require(targetRoleCode);
    // 授予者自身有效权限必须覆盖目标角色的全部权限点（不可授出自己没有的能力）
    Set<String> grantorPerms = permissionService.effective(grantor);
    Set<String> missing = target.permissionCodes().stream()
            .filter(c -> !grantorPerms.contains(c)).toList();
    if (!missing.isEmpty() && !grantor.isOwner())
        throw new BizException(FORBIDDEN, "不可授予超出自身权限的角色，缺少：" + missing);
    // 团队角色不得携带组织级权限点
    if ("TEAM".equals(scopeType) && target.hasPermissionOfLevel(PermLevel.TENANT))
        throw new BizException(PARAM_ERROR, "团队角色不可包含组织级权限");
}
```

### 4.1 功能权限点（Permission）

| `ops:diagnostic:read` | 只读诊断（失败问数脱敏、错误码统计） | ✔ | ✔ | ✔ | ✔ |

### 4.3 数据范围（DataScope）

| 枚举 | SQL 追加条件 | 说明 |
| --- | --- | --- |
| `ALL` | 不追加（平台域，跨租户） | 仅 `tenant_id=0` 身份，且必须配合 `admin:*` 权限点 |
| `TENANT` | 不追加（`tenant_id` 已由租户拦截器注入） | 组织内全可见 |
| `TEAM_AND_CHILD` | `AND (owner_uid=? OR team_id IN (current+children) OR visibility='TENANT')` | 本团队及子团队 + 组织级公开资源 + 自己的 |
| `TEAM` | `AND (owner_uid=? OR team_id=? OR visibility='TENANT')` | 仅当前团队 |
| `SELF` | `AND owner_uid=?` | 仅本人 |
| `CUSTOM` | 走 `resource_acl` 关联子查询 | 逐资源授权 |

**`visibility` 三值语义**（资源可见性，与数据范围正交）：

| 值 | 含义 | 典型 |
| --- | --- | --- |
| `PRIVATE` | 仅 `owner_uid` 与被 ACL 授权者 | 个人草稿驾驶舱 |
| `TEAM` | 团队成员可见 | 团队指标 |
| `TENANT` | 组织内全员可见 | 组织级数据源、公共指标库 |

存量数据迁移时全部置 `TENANT`（等价于升级前"组织内全可见"），**保证升级后用户不会突然看不到自己原来的指标**——这是数据范围落地最容易踩的用户体验事故。

### 4.4 判定管线（决策顺序）

```
请求 ─▶ ① 认证：JWT 验签 + 状态位（app_user.status=1、tenant.status=1、未过期）
              │ 失败 → 401 / 40001、40305、40304
              ▼
       ② 会话有效性：perm_version / token_version 比对（敏感变更即时吊销）
              │ 失败 → 401 / 40311（前端触发静默重登或跳登录）
              ▼
       ③ 粗粒度域门禁：Spring Security URL 规则
              /api/admin/** → hasAnyRole(SUPER_ADMIN, OPERATOR, AUDITOR, SUPPORT)
              /api/public/** → permitAll
              │ 失败 → 403 / 40301
              ▼
       ④ 功能权限点：@RequiresPermission 切面（含角色别名 @RequiresRole）
              │ 失败 → 403 / 40301
              ▼
       ⑤ 上下文完备性：需要团队的接口校验 currentTeamId（@RequiresTeam）
              │ 失败 → 403 / 40306
              ▼
       ⑥ 数据范围：DataScopeInterceptor 改写 SQL / Service 显式传范围
              │ 越界写 → 403 / 40310
              ▼
       ⑦ 资源 ACL：@CheckResourceOwner 或 Service 内 resourceAclService.can(...)
              │ 失败 → 403 / 40310
              ▼
       ⑧ 业务护栏：席位余量、配额（QuotaService）、并发（ConcurrencyGuard）、套餐能力位
              │ 失败 → 429 / 42901、42903、40308
              ▼
       ⑨ 执行 + 审计落库（写操作与越权拦截均记 auth_audit_log）
```

顺序不可调换的理由：②在③前是为了"被移除的成员立刻失效"；⑧在⑥⑦后是为了"越权请求不消耗配额"（与现有 `QuotaService` 置于并发护栏之前的既有约定一致）。

### 5.1 新增表总览（`aibi_meta`）

> **关键陷阱（必须照做）**：`team_member`、`user_role` 虽然带 `tenant_id`，但**登录时需要在 `TenantContext` 建立之前读取**（要用它们算出角色再签发 JWT）。若不列入 IGNORE 名单，`AibiTenantLineHandler.getTenantId()` 在无上下文时返回 `NullValue`，条件变成 `tenant_id = NULL` → **永远查不到行 → 所有人登录后角色为空集 → 全站 403**。这与现有 `app_user` 被列入 IGNORE 的原因完全一致。列入 IGNORE 后，登录链路必须按显式 `uid` / `tenant_id` 查询，且这两张表的**所有写操作**都必须显式带 `tenant_id` 条件（在 Service 层用 `assertTenantMatch()` 断言兜底）。

对列入 IGNORE 但带 `tenant_id` 的四张表（`team_member`/`user_role`/`invitation`/`invitation_apply`），统一约定：

1. **写操作必须显式带 `tenant_id`**：`Wrappers.<UserRole>lambdaUpdate().eq(UserRole::getTenantId, ctx.tenantId()).eq(...)`。
2. **登录后读取必须显式带 `tenant_id`**：解析出 `uid` 后，用 `uid → app_user.tenant_id` 反查，再按该 `tenant_id` 过滤。

## 6. 后端 API 权限机制

### 6.1 双层门禁

| 层 | 机制 | 粒度 | 职责 |
| --- | --- | --- | --- |
| L1 URL 粗粒度 | Spring Security `authorizeHttpRequests` | 路径前缀 | 域隔离：平台域必须持平台角色；公开域放行；其余必须认证 |
| L2 方法细粒度 | `@RequiresPermission` + AOP 切面 | 单个接口方法 | 功能权限点、数据范围、资源归属 |

L1 只回答"能不能进这个域"，L2 才回答"能不能干这件事"。两层都必须过，任一层拒绝即返回 403，不进入 Service。

```java
// common/security/SecurityConfig.java —— 在现有基础上扩展
.authorizeHttpRequests(auth -> auth
    // 公开域：认证页、邀请预览/接受、分享与大屏公开访问、健康检查
    .requestMatchers("/api/auth/login", "/api/auth/register", "/api/auth/identities",
                     "/api/auth/invitation/preview", "/api/auth/invitation/accept-anonymous",
                     "/api/auth/invitation/apply",
                     "/api/public/**", "/actuator/health", "/error").permitAll()
    // 平台运营域：必须持任一平台角色（细粒度权限点由 L2 判定）
    .requestMatchers("/api/admin/**", "/api/ops/**")
        .hasAnyRole("SUPER_ADMIN", "OPERATOR", "AUDITOR", "SUPPORT")
    // 组织治理域：必须认证（具体组织角色由 L2 判定，避免把角色写死在 URL 规则里）
    .requestMatchers("/api/org/**", "/api/member/**", "/api/team/**", "/api/invitation/**")
        .authenticated()
    .anyRequest().authenticated())
```

> ⚠️ 现有 `.requestMatchers("/api/admin/**").hasRole("SUPER_ADMIN")` 必须改为 `hasAnyRole(...)`，否则运营/审计账号进不了后台。更隐蔽的一处是 `JwtAuthFilter` 目前只把单个 `role` 转成**一个** `SimpleGrantedAuthority`，引入多平台角色后必须把 `prole` 拆分成集合逐个转 authority，否则 `hasAnyRole` 永远不命中。

### 6.2 注解与切面

```java
/** 功能权限点校验。logical=AND 时需全部具备，OR 时任一即可。 */
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface RequiresPermission {
    String[] value();
    Logical logical() default Logical.AND;
    /** 平台域接口：要求上下文 tenantId==0，防止组织身份越权访问平台接口 */
    boolean platformOnly() default false;
}

/** 角色校验（用于"整个角色"而非"单个权限点"的语义，如 OWNER 专属的转让/解散）。 */
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface RequiresRole {
    String[] value();
    RoleLevel level() default RoleLevel.TENANT;   // PLATFORM / TENANT / TEAM
    Logical logical() default Logical.OR;
}

/** 要求已选定团队上下文（团队级接口）。 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequiresTeam {
    boolean allowFallbackToDefault() default true;  // true=未选团队时回落 tenant.default_team_id
}

/** 资源归属校验：从方法入参提取资源 id，校验当前用户对该资源有指定权限。 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface CheckResourceAccess {
    String type();                       // DATASOURCE / METRIC / DASHBOARD / SHARE
    String idParam() default "id";       // 方法参数名
    String permission() default "READ";  // READ / WRITE / MANAGE
    String idSpEL() default "";          // 复杂入参用 SpEL，如 "#form.datasourceId()"
}
```

切面（`@Order(20)`：早于业务方法、晚于事务边界建立，确保拒绝时不产生任何写副作用）：

```java
@Aspect
@Component
@Order(20)
public class PermissionAspect {

    private final PermissionService permissionService;
    private final AuditService auditService;

    @Around("@annotation(rp) || @within(rp)")
    public Object check(ProceedingJoinPoint pjp, RequiresPermission rp) throws Throwable {
        AccessContext ctx = AccessContextHolder.require();          // 无上下文 → 40001
        if (rp.platformOnly() && !ctx.isPlatform()) {
            return deny(ctx, rp, "非平台身份访问平台接口");
        }
        Set<String> owned = permissionService.effectivePermissions(ctx);
        boolean ok = rp.logical() == Logical.AND
                ? owned.containsAll(List.of(rp.value()))
                : Arrays.stream(rp.value()).anyMatch(owned::contains);
        if (!ok) {
            return deny(ctx, rp, "缺少权限点 " + Arrays.toString(rp.value()));
        }
        return pjp.proceed();
    }

    /** 统一拒绝出口：写审计 + 抛 BizException（由 GlobalExceptionHandler 转 403 JSON）。 */
    private Object deny(AccessContext ctx, RequiresPermission rp, String reason) {
        auditService.recordDenied(ctx, rp.value(), reason);          // action=PERM_CHECK_DENIED
        throw new BizException(ErrorCode.FORBIDDEN, reason);
    }
}
```

**使用示例**（改造现有 Controller，只加注解、不动业务逻辑；方法级注解覆盖类级）：

### 6.3 权限解析与缓存失效

**不把权限点集合塞进 JWT**：权限点数十至上百个，塞进令牌会让每个请求头膨胀数 KB；且权限变更后旧令牌仍携带旧权限集，无法即时生效。JWT 只带**角色码 + 版本号**，权限点在服务端解析。

```
JWT claims（扩展后）
  sub   = username
  uid   = app_user.id
  iid   = user_identity.id
  tid   = tenant_id
  plan  = FREE / PRO / ENTERPRISE
  prole = 平台角色码，逗号分隔（组织身份为空串）
  trole = 组织角色码，逗号分隔
  team  = 当前团队 id（可空）
  scope = NORMAL / ASSIST（代客协助影子令牌）
  sid   = 会话 id（login_session.sid，用于精确吊销）
  pv    = 权限版本（签发时的 tenant.perm_version + app_user.token_version）
  iat / exp
```

四级缓存：

| 缓存 | key | value | TTL | 失效方式 |
| --- | --- | --- | --- | --- |
| 权限点字典 | `perm:dict` | `Map<code, Permission>` | 30min | 平台改字典时主动全量失效 |
| 角色权限 | `perm:role:{tenantId}:{roleCode}` | `Set<code>` | 10min | 自定义角色/override 变更时按 `tenantId` 失效 |
| 用户有效权限 | `perm:user:{tenantId}:{uid}:{teamId}` | `PermissionSet` | 5min | 角色授予/回收、成员移除、团队变更时按 `uid` 失效 |
| 版本号 | `perm:ver:{tenantId}`、`perm:tver:{uid}` | `long` | **30s** | 短 TTL，容忍最终一致 |

**分级吊销**（体验与安全的平衡，明确区分两类变更）：

| 变更类型 | 生效方式 | 用户感知 |
| --- | --- | --- |
| 新增权限点、调整自定义角色、加入团队、授予角色 | 缓存 TTL 内最终一致（≤5min） | 无感 |
| **移除成员、停用账号、停用租户、降级为 VIEWER、回收 OWNER、重置口令、协助授权终止** | `app_user.token_version++` / `tenant.perm_version++` + 置 `login_session.revoked_at`；`JwtAuthFilter` 比对 `pv` 失败立即 401 + `40311` | 被踢下线，提示"权限已变更，请重新登录" |

```java
// JwtAuthFilter 中的版本校验（解析 claims 之后、写入上下文之前）
long tokenPv = toLong(claims.get("pv"));
long currentPv = permVersionService.current(tenantId, uid);   // Caffeine 30s
if (tokenPv < currentPv || sessionService.isRevoked(claims.get("sid", String.class))) {
    writeRevoked(response);      // HTTP 401 {"code":40311,"message":"权限已变更，请重新登录"}
    return;                      // 不再放行，也不写入任何上下文
}
```

> 30s 的版本缓存是**有意的权衡**：完全实时校验会让每个请求多两次 DB 查询（4 核 4G 单机下 QPS 敏感）。对"移除成员"这类必须秒级生效的场景，额外走 `login_session.revoked_at` 按 `sid` 精确吊销（命中唯一索引，开销可控）。两者叠加即达成"普通变更 30s 内收敛、精确吊销即时生效"。

### 6.4 接口权限矩阵自动扫描（防漏配）

权限体系最容易腐化的地方是"新加了接口忘了挂权限点"。用启动期扫描把它变成**可见的运维指标**：

```java
@Component
public class ApiPermissionRegistry implements ApplicationRunner {

    /** 扫描 RequestMappingHandlerMapping 的全部映射 + @RequiresPermission，生成接口清单。 */
    @Override
    public void run(ApplicationArguments args) {
        RequestMappingHandlerMapping mapping = ctx.getBean(RequestMappingHandlerMapping.class);
        for (Map.Entry<RequestMappingInfo, HandlerMethod> e : mapping.getHandlerMethods().entrySet()) {
            for (String pattern : e.getKey().getPatternValues()) {
                for (RequestMethod m : e.getKey().getMethodsCondition().getMethods()) {
                    registry.put(m.name() + " " + pattern, new ApiEndpoint(
                            m.name(), pattern,
                            e.getValue().getBeanType().getSimpleName(),
                            e.getValue().getMethod().getName(),
                            resolvePermCode(e.getValue()),      // 方法级优先，回落类级
                            resolveResource(e.getValue())));    // @CheckResourceAccess
                }
            }
        }
        report();   // 日志输出未挂权限点的 fail-closed 域接口；严格模式下可直接拒绝启动
    }
}
```

产出三张视图（平台后台"权限字典"页）：

1. **接口权限矩阵**：全部接口 × 所需权限点 × 所需数据范围，可按模块过滤。
2. **未标注告警**：fail-closed 域中未挂 `@RequiresPermission` 的接口 → 红色高亮。
3. **孤儿权限点**：字典中存在但无任何接口/菜单/按钮引用的权限码 → 提示清理。

**fail-closed / fail-open 边界**（明确规则，避免"默认放行还是拒绝"的反复争论）：

| 域 | 未标注权限点时的行为 | 理由 |
| --- | --- | --- |
| `/api/admin/**`、`/api/ops/**` | **拒绝**（403） | 平台域一旦漏配即全局越权，代价不可接受 |
| `/api/member/**`、`/api/team/**`、`/api/org/**`、`/api/invitation/**`、`/api/datasource/**` | **拒绝**（403） | 涉及成员、凭证、组织治理 |
| `/api/semantic/**`、`/api/fewshot/**`、`/api/chart-rule/**`、`/api/config/**` | **拒绝**（403） | 影响全员问数口径，误改即全局效果劣化 |
| `/api/chat/**`、`/api/metric/**`、`/api/dashboard/**`、`/api/history/**`、`/api/favorite/**`、`/api/share/**`、`/api/quota/**`、`/api/manual/**`、`/api/theme/**` | **仅需认证**（放行 + 数据范围收敛） | 兼容存量，避免一次性改造 25 个 Controller 造成批量 403 |
| `/api/public/**`、`/api/auth/login\|register\|identities\|invitation/*` | 放行 | 匿名域 |

第三类必须在 P1 阶段逐步补齐注解并迁到 fail-closed（见 §13），迁移期用 `aibi.security.strict-domains` 配置项按域灰度开启，避免"改一批炸一批"。

### 6.5 数据范围的行级过滤

复用 MyBatis-Plus 3.5.5 自带的 `DataPermissionInterceptor`（与现有 `TenantLineInnerInterceptor` 同属 inner interceptor 链）：

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    // 顺序：先租户边界（框架强制、不可绕过），再团队/个人范围收敛
    interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(new AibiTenantLineHandler()));
    interceptor.addInnerInterceptor(new DataPermissionInterceptor(new AibiDataScopeHandler()));
    return interceptor;
}

/** 按当前上下文的 DataScope 追加范围条件；仅对 SCOPE_TABLES 生效，其余表跳过。 */
static class AibiDataScopeHandler implements MultiDataPermissionHandler {

    /** 参与团队级范围收敛的表（与 §5.5 增列清单一致）。 */
    private static final Set<String> SCOPE_TABLES = Set.of(
            "metric", "dashboard", "data_source", "query_favorite",
            "few_shot_example", "semantic_meta", "query_history", "share_link", "team");

    @Override
    public Expression getSqlSegment(Table table, Expression where, String mappedStatementId) {
        if (!SCOPE_TABLES.contains(normalize(table.getName()))) {
            return null;                                   // 不改写
        }
        AccessContext ctx = AccessContextHolder.get();
        if (ctx == null || ctx.isPlatform()) {
            return null;                                   // 平台域不做团队收敛（租户边界已足够）
        }
        return switch (ctx.dataScope()) {
            case ALL, TENANT -> null;                      // 组织内全可见：租户拦截器已足够
            case SELF -> eq("owner_uid", ctx.uid());
            case TEAM -> or(or(eq("owner_uid", ctx.uid()),
                               eq("team_id", ctx.currentTeamId())),
                            eq("visibility", "TENANT"));
            case TEAM_AND_CHILD -> or(or(eq("owner_uid", ctx.uid()),
                                         in("team_id", union(ctx.currentTeamId(), ctx.childTeamIds()))),
                                      eq("visibility", "TENANT"));
            case CUSTOM -> aclSubQuery(table.getName(), ctx);
        };
    }
}
```

**必须知道的三个陷阱**（本项目已踩过同类坑，不要重复）：

1. **jsqlparser 4.6 对非 ASCII 标识符不友好**。两个改写器都基于 jsqlparser 解析并重写 SQL；本项目已出现过"中文列名问数报 `50002`，根因是 JSqlParser 4.6 拒绝非 ASCII 标识符"。数据范围追加的列名固定 ASCII（`owner_uid`/`team_id`/`visibility`）本身安全，但**被改写的原 SQL 若含中文别名，改写过程同样会抛异常**。规避：元数据侧含中文别名的统计 Mapper 标 `@InterceptorIgnore(tenantLine="true", dataPermission="true")` 并显式传条件；问数链路执行的是租户业务库 SQL、不经 MyBatis-Plus，不受影响。
2. **`DataPermissionInterceptor` 对 JOIN/子查询/UNION 的改写有边界**。多表 JOIN 时它会给每张命中表都追加条件，可能把 LEFT JOIN 变成事实上的 INNER JOIN（右表条件不满足即整行消失，表现为"列表莫名少数据"）。规避：涉及 LEFT JOIN 的统计 Mapper 一律显式豁免 + 手写条件。
3. **`updateById` 默认忽略 null 字段**。移除成员后要把资源 `owner_uid` 置空、邀请要清空 `target_email`/`expire_at` 时，用实体 `updateById` 会**静默失效**（字段纹丝不动、也不报错）。规避：所有"置空"语义统一用 `Wrappers.lambdaUpdate().set(Entity::getXxx, null)`，与现有 `UserAdminService.update` 的写法保持一致。

### 6.6 资源级 ACL 判定

```java
@Service
public class ResourceAclService {

    /** 资源访问判定：所有者 → visibility → 团队范围 → ACL，任一命中即通过。 */
    public boolean can(AccessContext ctx, String resourceType, Long resourceId, String required) {
        ResourceRef ref = loader.load(resourceType, resourceId);      // 各模块提供 ResourceLoader
        if (ref == null) {
            throw new BizException(ErrorCode.RESOURCE_FORBIDDEN, "资源不存在或无权访问");
        }
        TenantAssertion.assertMatch(ref.tenantId(), ctx.tenantId());  // 跨租户直接失败（防御纵深）
        if (Objects.equals(ref.ownerUid(), ctx.uid())) return true;   // 所有者全权
        if ("TENANT".equals(ref.visibility()) && !"MANAGE".equals(required)) return true;
        if (ctx.dataScope() == DataScope.TENANT) return true;
        if (inTeamScope(ctx, ref.teamId(), ref.visibility())) return true;
        return aclHit(ctx, resourceType, resourceId, required);       // resource_acl 逐条判定
    }

    /** MANAGE 需所有者或 ACL(MANAGE)；WRITE 需 MANAGE ∪ WRITE ∪ 所有者；READ 最宽。 */
    private boolean aclHit(AccessContext ctx, String type, Long id, String required) {
        int need = levelOf(required);            // READ=1 WRITE=2 MANAGE=3
        List<ResourceAcl> rows = aclMapper.selectList(Wrappers.<ResourceAcl>lambdaQuery()
                .eq(ResourceAcl::getResourceType, type)
                .eq(ResourceAcl::getResourceId, id)
                .eq(ResourceAcl::getStatus, 1)
                .and(w -> w.and(x -> x.eq(ResourceAcl::getPrincipalType, "USER")
                                      .eq(ResourceAcl::getPrincipalId, ctx.uid()))
                         .or(x -> x.eq(ResourceAcl::getPrincipalType, "TEAM")
                                  .in(ResourceAcl::getPrincipalId, ctx.allTeamScopeIds()))
                         .or(x -> x.eq(ResourceAcl::getPrincipalType, "ROLE")
                                  .in(ResourceAcl::getPrincipalCode, ctx.orgRoles())))
                .and(w -> w.isNull(ResourceAcl::getExpireAt)
                           .or().gt(ResourceAcl::getExpireAt, LocalDateTime.now())));
        return rows.stream().anyMatch(r -> levelOf(r.getPermission()) >= need);
    }
}
```

> 返回"资源不存在"还是"无权限"要统一：本项目现有 `DATASOURCE_NOT_FOUND(40401)` 的文案是"数据源不存在或无权访问"，**刻意模糊**以避免资源枚举探测。新增资源类型沿用同一策略（对外不区分 404/403），但审计日志内部记录真实原因。

### 6.7 令牌签发、切换组织与强制下线

| 场景 | 接口 | 行为 |
| --- | --- | --- |
| 登录（单身份） | `POST /api/auth/login` | 校验 identity 口令 → 查该 identity 的 `app_user` 身份列表 → 恰好 1 个则直接签发 JWT |
| 登录（多身份） | `POST /api/auth/login` | 返回 `needSelectIdentity=true` + 身份列表（组织名、角色、套餐），**不签发业务令牌**，只给 TTL 5min 的 `select_token` |
| 选择身份 | `POST /api/auth/identities/select` | 用 `select_token` 换正式 JWT；过期需重新登录 |
| 切换组织 | `POST /api/auth/switch-identity` | 需已登录；校验目标身份属于同一 `identity_id` → 吊销当前 `sid` → 签发新 JWT → 记审计 |
| 切换团队 | `POST /api/auth/switch-team` | 需已登录；校验 `team_member` 存在且 status=1 → 签发新 JWT（`team` claim 变更，`sid` 不变） |
| 强制下线 | `POST /api/member/{uid}/revoke-session` | 置 `login_session.revoked_at` + `app_user.token_version++` |
| 主动登出 | `POST /api/auth/logout` | 置当前 `sid` 的 `revoked_at` |

> ⚠️ **现有 `logout` 是空实现**（`AuthController.logout()` 直接 `return R.ok()`，注释写的是"无状态 JWT 的登出仅需前端丢弃令牌"）。引入 `login_session` 后必须改为真吊销，否则"移除成员即时生效"的承诺无法兜底——被移除的成员拿着旧令牌可以一直用到自然过期（当前配置 `expire-minutes:120`，即最多 2 小时）。这是本次改造中**最容易漏且后果最严重**的一处。

### 7.2 permission store

```typescript
// stores/permission.ts
export const usePermissionStore = defineStore('permission', () => {
  const codes = ref<Set<string>>(new Set())
  const menus = ref<Set<string>>(new Set())
  const dataScope = ref<DataScope>('SELF')
  const orgRoles = ref<string[]>([])
  const teamRoles = ref<string[]>([])
  const platformRoles = ref<string[]>([])
  const teams = ref<TeamBrief[]>([])
  const currentTeamId = ref<number | null>(null)
  const seat = ref<{ used: number; limit: number }>({ used: 0, limit: -1 })
  const permVersion = ref(0)
  const assistMode = ref(false)          // 平台协助中（顶栏红色横幅）
  const loaded = ref(false)

  /** 单点权限判定：全部 UI 门禁都走这里，禁止各处自行拼判断。 */
  function has(code: string): boolean { return codes.value.has(code) }
  function hasAny(...list: string[]): boolean { return list.some(c => codes.value.has(c)) }
  function hasAll(...list: string[]): boolean { return list.every(c => codes.value.has(c)) }
  function hasRole(...list: string[]): boolean {
    const all = [...platformRoles.value, ...orgRoles.value, ...teamRoles.value]
    return list.some(r => all.includes(r))
  }
  /** 数据范围能力位：用于"能否看到他人资源"的 UI 提示与列展示 */
  const canSeeOthers = computed(() =>
    ['ALL', 'TENANT', 'TEAM_AND_CHILD', 'TEAM'].includes(dataScope.value))

  async function load(): Promise<void> {
    const p = await permissionApi.current()
    codes.value = new Set(p.permissions)
    menus.value = new Set(p.menus)
    dataScope.value = p.dataScope
    orgRoles.value = p.orgRoles
    teamRoles.value = p.teamRoles
    platformRoles.value = p.platformRoles
    teams.value = p.teams
    currentTeamId.value = p.currentTeamId
    seat.value = { used: p.tenant.seatUsed, limit: p.tenant.seatLimit }
    permVersion.value = p.permVersion
    assistMode.value = p.assistMode
    loaded.value = true
  }

  /** 切换团队：换 JWT → 重载权限（跳转与 store 重置由调用方控制）。 */
  async function switchTeam(teamId: number): Promise<void> {
    const res = await authApi.switchTeam(teamId)
    setToken(res.token)
    await load()
  }

  /** 登出 / 切换组织时必须调用：不留半个旧上下文。 */
  function reset(): void {
    codes.value = new Set(); menus.value = new Set(); loaded.value = false
    orgRoles.value = []; teamRoles.value = []; platformRoles.value = []
    teams.value = []; currentTeamId.value = null; permVersion.value = 0; assistMode.value = false
  }

  return { codes, menus, dataScope, orgRoles, teamRoles, platformRoles, teams,
           currentTeamId, seat, permVersion, assistMode, loaded, canSeeOthers,
           has, hasAny, hasAll, hasRole, load, switchTeam, reset }
})
```

### 7.3 路由守卫升级

`meta` 从单一 `role` 升级为可组合字段，并**保持对现有 `meta.role='SUPER_ADMIN'` 的向后兼容**（避免一次性改 6 个 admin 路由）：

```typescript
// types/router.d.ts —— Vue 3 的模块增强必须写在模块文件中（本项目已有同类经验）
declare module 'vue-router' {
  interface RouteMeta {
    title?: string
    icon?: string
    hidden?: boolean
    public?: boolean
    fullscreen?: boolean
    perm?: string                 // 单个权限点（最常用）
    perms?: string[]              // 多个权限点
    permLogical?: 'AND' | 'OR'    // 配合 perms，默认 OR
    roles?: string[]              // 角色码（OWNER 专属页等"整角色"语义）
    requireTeam?: boolean         // 需已选团队
    role?: string                 // @deprecated 兼容存量，等价于 roles:[role]
  }
}

router.beforeEach(async (to) => {
  const userStore = useUserStore()
  const permStore = usePermissionStore()

  if (to.meta.public) {
    if (userStore.isLoggedIn && (to.name === 'login' || to.name === 'register')) {
      return { path: userStore.homePath }
    }
    return true
  }
  if (!getToken()) {
    return { path: '/login', query: { redirect: to.fullPath } }
  }

  // 首屏或刷新后：权限集合尚未加载 → 先拉取（失败即视为登录态失效）
  if (!permStore.loaded) {
    try {
      await Promise.all([userStore.loadMe(), permStore.load()])
    } catch {
      clearAuth()
      return { path: '/login', query: { redirect: to.fullPath, reason: 'expired' } }
    }
  }

  // 角色门禁（含存量 meta.role 兼容）
  const needRoles = to.meta.roles ?? (to.meta.role ? [to.meta.role] : undefined)
  if (needRoles?.length && !permStore.hasRole(...needRoles)) {
    return { path: '/403', query: { from: to.fullPath } }
  }

  // 权限点门禁
  const needPerms = to.meta.perm ? [to.meta.perm] : to.meta.perms
  if (needPerms?.length) {
    const ok = to.meta.permLogical === 'AND'
      ? permStore.hasAll(...needPerms)
      : permStore.hasAny(...needPerms)
    if (!ok) return { path: '/403', query: { from: to.fullPath } }
  }

  // 团队上下文门禁：未选团队且无默认团队 → 引导到团队选择
  if (to.meta.requireTeam && !permStore.currentTeamId) return { path: '/org/teams/select' }

  return true
})
```

### 7.4 动态菜单（替换硬编码 navItems）

现有 `AppLayout.vue` 里 `navItems` 是写死的 9 项数组，新增页面要同时改路由表和这个数组（已存在不一致：路由有 `manual` 但 `navItems` 没有）。改为**路由表驱动 + 权限过滤**的单一来源：

```typescript
// composables/useMenus.ts
export interface MenuNode { path: string; title: string; icon?: string; children?: MenuNode[] }

/** 菜单顺序即路由 children 顺序；权限码取 route.meta.perm/perms。 */
export function useMenus(rootPath = '/') {
  const router = useRouter()
  const permStore = usePermissionStore()

  const build = (routes: RouteRecordRaw[], basePath = ''): MenuNode[] =>
    routes
      .filter(r => !r.meta?.hidden && !r.meta?.public)
      .filter(r => {
        if (r.meta?.roles?.length && !permStore.hasRole(...r.meta.roles)) return false
        const perms = r.meta?.perm ? [r.meta.perm] : r.meta?.perms
        if (!perms?.length) return true                      // 未声明权限点的菜单默认展示
        return permStore.hasAny(...perms)
      })
      .map(r => {
        const path = r.path.startsWith('/') ? r.path : `${basePath}/${r.path}`.replace(/\/+/g, '/')
        const children = r.children?.length ? build(r.children, path) : undefined
        return { path, title: (r.meta?.title as string) ?? '',
                 icon: r.meta?.icon as string, children }
      })
      .filter(n => n.title && (!n.children || n.children.length))   // 子项全被过滤掉的父项也隐藏

  const menus = computed(() => {
    void permStore.codes                                       // 显式建立响应式依赖
    const root = router.options.routes.find(r => r.path === rootPath)
    return root?.children ? build(root.children) : []
  })

  return { menus }
}
```

```vue
<!-- AppLayout.vue：删除 navItems 数组，改用 useMenus() -->
<nav class="nav">
  <router-link v-for="item in menus" :key="item.path" :to="item.path" class="nav-item"
               :class="{ active: activePath === item.path }">
    <el-icon :size="18"><component :is="item.icon" /></el-icon>
    <span v-show="!appStore.sidebarCollapsed" class="nav-label">{{ item.title }}</span>
    <span v-if="activePath === item.path" class="nav-active-bar" />
  </router-link>
</nav>
```

> `computed` 内必须**显式触碰** `permStore.codes`（上面第一行 `void permStore.codes`）：`load()` 里是 `codes.value = new Set(...)` 整体替换，`ref` 的 setter 会触发依赖，所以实际有效；保留这行是为了将来改成 `reactive(new Set())` 或改成 `codes.value.add()` 局部变更时不至于静默失效（菜单不刷新）。这类"看起来响应式其实不是"的坑值得在代码里留注释。

### 7.5 按钮级权限：三种手段与选型

| 手段 | 用法 | 响应式 | 适用 |
| --- | --- | --- | --- |
| `v-if="can('x')"` | 模板内联 | ✔ 天然响应式 | **首选**，绝大多数场景 |
| `<PermGuard code="x">` 组件 | 包裹 | ✔ 天然响应式 | 需"无权时展示禁用态 + tooltip"而非直接移除 |
| `v-perm="'x'"` 指令 | 属性 | ✗ **需手动 watch** | 静态工具条、第三方组件插槽内不便用 `v-if` 时 |

```typescript
// directives/perm.ts
/**
 * 按钮级权限指令。
 * ⚠️ 自定义指令不会随 store 变化自动重算（Vue 只在组件重渲染时调 updated），
 *    故内部自行 watch 权限版本号，切换团队/权限变更后主动重判，
 *    避免"权限已收回但按钮还在"。
 * 修饰符：.disable —— 无权时置 disabled + tooltip 说明，而非移除元素（保留可发现性）。
 */
export const vPerm: Directive<HTMLElement, string | string[]> = {
  mounted(el, binding) {
    const permStore = usePermissionStore()
    const apply = () => {
      const codes = Array.isArray(binding.value) ? binding.value : [binding.value]
      const ok = codes.some(c => permStore.has(c))
      if (ok) {
        el.style.removeProperty('display')
        el.removeAttribute('disabled')
        el.classList.remove('is-disabled')
      } else if (binding.modifiers.disable) {
        el.setAttribute('disabled', 'disabled')
        el.classList.add('is-disabled')
        el.setAttribute('title', '当前角色无权执行此操作')
      } else {
        el.style.display = 'none'
      }
    }
    apply()
    ;(el as any).__permStop = watch(() => permStore.permVersion, apply)
  },
  unmounted(el) { (el as any).__permStop?.() }
}
```

```vue
<!-- components/PermGuard.vue：无权时渲染禁用态占位，保留功能可发现性 -->
<script setup lang="ts">
import { computed } from 'vue'
import { usePermissionStore } from '@/stores/permission'
const props = withDefaults(defineProps<{
  code?: string; codes?: string[]; logical?: 'AND' | 'OR'
  mode?: 'hide' | 'disable'; tip?: string
}>(), { mode: 'hide', logical: 'OR', tip: '当前角色无权执行此操作' })

const allowed = computed(() => {
  const list = props.code ? [props.code] : (props.codes ?? [])
  if (!list.length) return true
  return props.logical === 'AND' ? permStore.hasAll(...list) : permStore.hasAny(...list)
})
</script>
<template>

</template>
```

### 7.7 401/403 统一处理与降级体验

`api/request.ts` 拦截器扩展（现有只处理 401 跳登录）：

| 响应码 | 前端行为 |
| --- | --- |
| `40001` 未认证 | 清 auth + `permStore.reset()` → 跳 `/login?redirect=` |
| `40311` 权限已变更 | 同上，但提示"您的权限已变更，请重新登录"（`reason=revoked`） |
| `40301` 无权限 | **不跳转**，`ElMessage.error(msg)`；若整页无权则跳 `/403` |
| `40310` 资源无权 | 提示"资源不存在或无权访问"，返回列表页 |
| `40306` 缺团队上下文 | 跳 `/org/teams/select` |
| `40315` 需选组织 | 跳 `/select-org`（登录流程内） |
| `40305`/`40304` 租户停用/过期 | 全屏阻断页（不可继续操作，仅可联系管理员） |
| `40317`/`40308` 席位不足 | 引导至升级套餐 / 清理闲置成员 |
| `42901`/`42903` 配额耗尽 | 提示升级入口（现有逻辑保留） |

新增 `/403` 页：展示"缺少的权限点名称 + 应联系的角色（组织管理员）+ 返回按钮"，比裸 403 有用得多。

> SSE 链路需单独处理：现有 fetch 版 SSE 客户端靠 `result`/`error` 终止事件复位加载态。权限变更导致的 401/403 在 SSE 上不会走 `request.ts` 拦截器，必须在 SSE 错误分支里同样识别 `40311` 并清登录态，否则问数面板会永远卡在加载中。

## 8. 组织邀请机制

### 8.1 四种通道

| 通道 | 触发者 | 载体 | 典型场景 | 席位控制 | 审批 |
| --- | --- | --- | --- | --- | --- |
| `LINK` 邀请链接 | ADMIN / TEAM_OWNER | 可复制转发的 URL（含 `invite_token`） | 团队群里发链接，成员自助加入 | `seats`（可 -1 不限） | 可选 `require_approval` |
| `EMAIL` / `SMS` 定向邀请 | ADMIN | 邮件/短信（含一次性链接） | 精确邀请某人，预设角色与团队 | 每封 `seats=1` | 通常免审批 |
| `BATCH` 批量导入 | ADMIN | CSV/Excel 上传（复用 `FileStorageService`） | 组织初始化，一次导入几十人 | 受 `tenant.seat_limit` 余量硬约束 | 生成后统一待确认 |
| `APPLY` 申请加入 | 申请人自己 | 组织码 / 邀请链接 → 提交申请 | 成员主动申请，管理员把关 | 审批通过才占席位 | **必须**审批 |

### 8.2 邀请状态机

```
                         ┌─────────── REVOKED（管理员撤销，终态）
                         │
   创建 ─▶ DRAFT ─发送─▶ SENT ─┬─接受且 require_approval=0 ────────▶ ACCEPTED（终态）
                         ▲       │
                         │       └─接受且 require_approval=1 ─▶ PENDING ─┬─通过─▶ APPROVED ─▶ ACCEPTED
      惰性判定 + 定时兜底 │                                          └─拒绝─▶ REJECTED（终态）
                         │
                         └──── EXPIRED（expire_at 到期 / seats 用尽，终态）
```

- `DRAFT` 用于批量导入的"先生成后统一发送"；单条邀请直接进 `SENT`。
- `EXPIRED` 由**惰性判定 + 定时兜底**双保险：接受时校验 `expire_at`（惰性，主路径），另有每小时任务把过期行置 `EXPIRED`（避免列表长期显示"有效"）。只靠定时任务会出现"任务未跑到就接受了过期邀请"。
- 状态流转全部集中在 `InvitationService.transit(id, from, to)`，用 `UPDATE ... WHERE status = ?` 的 CAS 语义防并发重复流转（返回 0 行即表示已被其他请求改过，重读后报当前状态）。

### 8.3 接受邀请的事务时序（关键实现）

```
被邀请人点击链接
   │
   ▼
① GET /api/auth/invitation/preview?token=xxx        （匿名可访问）
   校验 token_hash 命中、status ∈ {SENT, APPROVED}、未过期、席位未满
   → 返回：组织名、预设角色名、团队名、是否需审批、是否需登录
   ⚠ 不返回成员列表、数据源、业务信息（防邀请链接成为组织信息侦察入口）
   │
   ▼
② 身份归并
   ├─ 已登录（identity_id 已知）
   │    ├─ 定向邀请且 target_email 非空 → 校验 identity.email == target_email，不符 → 40307
   │    └─ allow_domain 非空 → 校验邮箱域，不符 → 40307
   └─ 未登录
        ├─ need_login=1 → 跳登录/注册页，带 redirect=/invite/accept?token=xxx
        └─ need_login=0 → 走「邀请注册」：填邮箱+口令 → 建 user_identity
   │
   ▼
③ 组织内身份解析（POST /api/auth/invitation/accept，事务开始）
   ├─ 该 identity 在此 tenant 已有 app_user
   │    ├─ status=1 → 幂等返回"已是成员"（不重复占席位）
   │    └─ status=0（曾被移除）→ 若 require_approval 未强制为真则拒绝（见 §8.5），否则复活该行
   └─ 无 → 新建 app_user（tenant_id、username 按下方规则生成、identity_id、role='USER'）
   │
   ▼
④ 席位原子占位（两条 UPDATE 同事务，任一 affectedRows=0 即整体回滚）
   UPDATE invitation SET used_count = used_count + 1
    WHERE id = ? AND status IN ('SENT','APPROVED')
      AND (seats < 0 OR used_count < seats)
      AND (expire_at IS NULL OR expire_at > NOW());
   -- 0 行 → 40308 INVITE_EXHAUSTED / 40309 INVITE_EXPIRED

   UPDATE tenant SET seat_used = seat_used + 1
    WHERE id = ? AND status = 1
      AND (seat_limit < 0 OR seat_used < seat_limit)
      AND (expire_at IS NULL OR expire_at > NOW());
   -- 0 行 → 40317 SEAT_LIMIT_EXCEEDED / 40305 租户停用 / 40304 租户过期
   ⚠ 必须用条件 UPDATE 而非"先 SELECT 再 INSERT"，否则并发接受同一邀请会超发席位
   │
   ▼
⑤ require_approval=1 → 建 invitation_apply(PENDING) + invitation.status=PENDING
   事务提交，返回"待审批"（此时已占席位，拒绝时必须回退 seat_used）
   require_approval=0 → 继续 ⑥⑦⑧
   │
   ▼
⑥ 角色授予
   INSERT user_role(tenant_id, uid, role_code=invitation.role_code, scope_type='TENANT', scope_id=0)
   [custom_role_id 非空时改授自定义角色]
   ⚠ 服务端重跑 §3.6 的防提权校验（校验对象是 invited_by，不是接受者）
   ⚠ 写入必须显式带 tenant_id（user_role 在 IGNORE 名单，不会自动注入）
   │
   ▼
⑦ 团队归属
   INSERT team_member(tenant_id, team_id, uid, team_role=invitation.team_role, invited_by)
   [team_id 为空则用 tenant.default_team_id]
   INSERT user_role(..., scope_type='TEAM', scope_id=team_id, role_code=team_role)
   ⚠ 捕获 DuplicateKeyException → 视为已在团队，不报错（幂等）
   │
   ▼
⑧ 收尾（事务提交）
   - app_user.current_team_id = team_id；app_user.status = 1
   - tenant.perm_version = perm_version + 1
   - auth_audit_log(action='INVITE_ACCEPT', target_uid=uid,
                    detail={invitationId, roleCode, teamId, channel})
   - 返回 AuthResponse（新 JWT）+ 组织信息 → 前端直接进入该组织工作台
```

**`username` 生成规则**（`app_user.username` 全局唯一约束保持不变）：

1. 定向邀请：取邮箱前缀，冲突则追加 `+{tenantId}`，再冲突追加随机 4 位（`zhangwei` → `zhangwei+7` → `zhangwei+7a3f9`）。
2. 链接邀请且申请人自填：直接用其填写值，冲突即返回 `40002` 提示换名。
3. 生成后**必须再查一次唯一性**并在 `INSERT` 处捕获 `DuplicateKeyException` 重试一次——`uk_username` 是全局唯一索引，并发接受同一邀请时存在竞态，仅靠先查后插不够。

### 8.4 席位与配额

| 套餐 | `seat_limit` 默认 | 团队数上限 | 自定义角色数 | 说明 |
| --- | --- | --- | --- | --- |
| `FREE` | 3 | 1（仅默认团队） | 0 | 个人版即此档；3 席位是增长钩子 |
| `PRO` | 20 | 10 | 5 | |
| `ENTERPRISE` | -1（不限） | -1 | -1 | 按合同可设具体值 |

- 席位计数规则：`seat_used` 在移除成员时 `-1`；成员被**停用**（`status=0`）时**不减**（停用成员仍占席位，防"停用刷席位"绕过限制；如需释放由 OWNER 显式删除）。
- 席位与次数配额是**两个独立维度**：`seat_limit` 管人数，`daily_limit`/`total_limit` 管问数次数（现有 `QuotaService` 逻辑不变）。用量按团队归集（`query_history.team_id`），支撑"团队级用量报表"与内部分摊。
- 席位不足时的降级策略：`40317` 返回体带 `seatLimit`/`seatUsed`，前端引导至"升级套餐"或"清理闲置成员"（`billing:usage:read` 页展示 30 天未登录成员清单）。

### 8.5 安全设计

| 风险 | 对策 |
| --- | --- |
| token 泄露即被滥用 | 库中只存 `token_hash = SHA-256(token)`（十六进制，`CHAR(64)`），明文仅在创建响应中返回一次；`SecureRandom` 32 字节 → Base64URL（43 字符） |
| 链接被转发到组织外 | `target_email`（定向锁定）、`allow_domain`（限邮箱域，如 `@example.com`）、`seats`（限次数）、`expire_at`（限时间）、`need_login=1`（须登录态接受）、`require_approval=1`（人工把关） |
| 暴力枚举 token | 43 字符 Base64URL ≈ 256 bit 熵，不可枚举；额外对 `preview`/`accept` 按 IP + token 双维度限流（复用现有 `ConcurrencyGuard` 思路），连续 5 次失败锁 15min |
| 邀请提权 | 创建时校验 `role_code` 的权限集 ⊆ 创建者有效权限集（§3.6 `assertCanGrant`）；`OWNER`/`SUPER_ADMIN` 不可作为邀请角色；`custom_role` 须属于本租户 |
| 并发超发席位 | §8.3 ④ 的两条条件 UPDATE 原子占位 |
| 跨租户邀请 | `invitation` 带 `tenant_id`，接受链路手动 `TenantContext.set` 后所有写入自动带租户；`user_role`/`team_member` 写入前 `TenantAssertion` |
| 已移除成员复用旧邀请 | 接受时若发现 `app_user.status=0` 且存在 `auth_audit_log(MEMBER_REMOVE)` 记录，**强制要求 `require_approval=1`**（防离职员工拿手里的旧链接自行回来） |
| 邀请链接钓鱼 | `preview` 页展示组织全名 + 平台域名 + "请确认是您期望加入的组织"提示；邮件模板含组织名与邀请人昵称 |
| 邀请列表泄露邮箱 | 列表接口对 `target_email` 做部分脱敏（`zh***@example.com`），仅 `member:member:write` 以上可看完整值 |

### 8.6 成员生命周期

| 事件 | 触发 | 席位 | 会话 | 资源处理 | 审计 action |
| --- | --- | --- | --- | --- | --- |
| 加入 | 接受邀请 / 管理员直建 | `seat_used+1` | — | — | `MEMBER_ADD` / `INVITE_ACCEPT` |
| 角色变更 | `PUT /api/member/{uid}/roles` | 不变 | `token_version++`（降级即时生效） | — | `ROLE_GRANT` / `ROLE_REVOKE` |
| 团队变更 | `PUT /api/team/{id}/members` | 不变 | 换 JWT（`team` claim） | 其 PRIVATE 资源留在原团队 | `MEMBER_UPDATE` |
| 停用 | `PUT /api/member/{uid}` status=0 | **仍占** | 立即吊销全部 `sid` | 保留 | `MEMBER_DISABLE` |
| 移除 | `DELETE /api/member/{uid}` | `seat_used-1` | 立即吊销 | 见下方策略 | `MEMBER_REMOVE` |
| 主动退出 | `POST /api/member/self/leave` | `seat_used-1` | 立即吊销 | 同上；OWNER 拦截 `40314` | `MEMBER_LEAVE` |
| 转让所有权 | `POST /api/org/transfer-owner` | 不变 | 双方 `token_version++` | — | `OWNER_TRANSFER`（高危，二次确认 + 双方通知） |
| 解散团队 | `DELETE /api/team/{id}` | 不变 | 相关成员换 JWT | 团队资源 `team_id → default_team_id`，`visibility` 保持 | `TEAM_DISSOLVE` |
| 解散组织 | `POST /api/org/dissolve` | 全部释放 | 全员吊销 | 软删（`tenant.status=0` + `dissolved_at`），保留 30 天可恢复，之后归档 | `TENANT_DISSOLVE` |

**资源归属策略**（移除成员时最容易被忽略、也最容易造成数据丢失或泄露的环节）：

```
被移除成员 uid 名下的资源
   │
   ├─ visibility='TENANT' 或 'TEAM' 的资源（组织/团队资产）
   │     → 保留，owner_uid 改为 tenant.owner_uid（组织所有者代管）
   │     → detail 中保留原 owner_uid，审计可追溯
   │     ⚠ 置空/改写 owner_uid 必须用 lambdaUpdate().set(...)，updateById 会静默忽略 null
   │
   ├─ visibility='PRIVATE' 的资源（个人草稿）
   │     → 保留 30 天（打 owner_removed_at 标记），期间 OWNER 可认领
   │     → 30 天后由定时任务软删
   │
   ├─ 有效的分享链接（share_link）与大屏公开令牌（dashboard.share_token）
   │     → **立即失效**（share_link.status=0 / dashboard.share_token 置空）
   │     ⚠ 否则被移除成员仍能通过自己发出的公开链接间接读取组织数据 —— 这是真实漏洞，
   │        且因为公开链接不走 JWT，前面的会话吊销完全拦不住它
   │
   ├─ 该成员创建的邀请（invitation, invited_by=uid, status ∈ {DRAFT,SENT,PENDING}）
   │     → 全部置 REVOKED（防离职员工的邀请链接继续拉人）
   │
   ├─ 该成员授予他人的 resource_acl（granted_by=uid）
   │     → 保留（授权属于组织而非个人），但在组织设置页提示 OWNER 复核
   │
   └─ query_history / query_favorite
         → 历史保留（审计与计费用），收藏随人走（软删）
```

### 9.3 代客协助授权（SUPPORT 的最小权限通道）

问题：客户报障时，支持人员需要看到租户侧的真实上下文；但直接把支持人员加成租户成员，等于永久开放且不可控。

```
① SUPPORT 在 /admin/assist 发起申请
   { tenantId, reason, needScope: ['READ_ONLY_DIAGNOSTIC'], durationHours: 2 }
   → 落 auth_audit_log(action='ASSIST_REQUEST')，通知租户 OWNER（邮件 + 站内信）

② 租户 OWNER 在组织设置「协助授权」页审批
   通过 → 签发影子令牌（login_session.scope='ASSIST'，JWT claim scope='ASSIST'）
   拒绝 → 记审计，SUPPORT 收到拒绝原因

③ SUPPORT 持影子令牌访问租户域
   - PermissionService 检测到 scope=ASSIST 时，从有效权限集中剔除全部
     write / delete / manage / execute / assign / publish 动作
   - 数据源凭证接口硬拒绝（CredentialCipher 解密路径检查 scope，ASSIST 一律不解密）
   - 问数执行被禁（不消耗租户配额、不产生业务查询）
   - 前端 assistMode=true → 顶栏红色横幅 + 全部写按钮隐藏
   - 每个请求记 auth_audit_log(actor_type='SUPPORT')

④ 到期 / 终止
   - durationHours 到 → 定时任务置 revoked_at
   - 租户 OWNER 点「立即终止协助」→ 立即吊销
   - ASSIST 会话在 /admin/assist 列表实时可见（谁、哪个租户、还剩多久）
```

**红线**（写入代码硬断言，不依赖流程约束）：`scope=ASSIST` 的令牌**永不**能调用 `datasource:*:write`、`datasource:config:test`、任何 `admin:*:write`、`member:*`、`org:*`。在 `PermissionAspect` 入口处前置一份**硬编码拒绝清单**，即使权限字典被误配也无法越界。

### 10.2 实现与约束

- `AuditService.record(action, ...)` **异步写入**（`@Async`，复用现有 `AsyncConfig` 的线程池），失败只告警不阻断主流程——审计不可反过来把业务搞挂。
- 但**高危事件同步写**（`OWNER_TRANSFER`、`MEMBER_REMOVE`、`TENANT_DISSOLVE`、`ASSIST_APPROVE`）：宁可事务慢一点，也要保证这些事件与业务变更同生同死。
- `detail` 存 JSON，**禁存口令、`password_hash`、`api_key_cipher`、`password_cipher`、完整邀请 token**；数据源凭证只记 `datasourceId` 与 `name`。
- 保留期：`auth_audit_log` 按 `created_at` 分区或定时归档，在线保留 180 天，归档至对象存储/单独表保留 2 年（私有化部署可配）。
- 审计查询自身也记审计（`AUDIT_EXPORT`），防止"看日志的人无人看"。

## 11. 迁移与兼容策略

### 11.1 总体原则

1. **不停机**：全部结构变更用 `SchemaMigration` 幂等增列/建表（已有机制），新表用 `metadata-schema.sql` 的 `CREATE TABLE IF NOT EXISTS`。
2. **默认值等价于升级前行为**：`visibility='TENANT'`、`seat_limit=-1`、`team_id=NULL`——保证升级后用户看不到任何差异。
3. **旧字段保留不删**：`app_user.role` 保留（作为平台角色回退与兼容读取源），至少两个版本后才考虑下线。
4. **可回滚**：每个阶段可单独回退（前端保留 `meta.role` 兼容分支；后端保留 `aibi.rbac.enabled=false` 开关，关闭时回退到"仅 SUPER_ADMIN/USER 二元判定"）。

### 11.2 数据回填（`SchemaMigration` V9 + `DataSeeder` 扩展）


回填顺序（一个事务内完成，失败整体回滚）：

| 步 | 操作 | 幂等保障 |
| --- | --- | --- |
| 1 | 为每个 `app_user` 生成/归并 `user_identity`：**按 `email` 分组**，同 email 复用一个 identity；email 为 NULL 则每人一个（MySQL 唯一索引允许多个 NULL）；`password_hash` 直接复制 | `WHERE identity_id IS NULL` |
| 2 | 为每个 `tenant` 建默认团队 `code='default'`、`name='默认空间'`，回写 `tenant.default_team_id` | `INSERT ... SELECT` + `uk_tenant_code` 去重 |
| 3 | 把每个租户的全部 `app_user` 加入默认团队：`team_role='TEAM_OWNER'`（存量每租户只有1人，即注册者，给负责人合理） | `uk_team_uid` 去重 |
| 4 | 把 `app_user.role` 映射到 `user_role`：`SUPER_ADMIN` → `scope_type='PLATFORM', scope_id=0, role_code='SUPER_ADMIN'`；`USER` → `scope_type='TENANT', scope_id=0, role_code='OWNER'` | `uk_uid_role_scope` 去重 |
| 5 | 回写 `tenant.owner_uid` = 该租户最早的 `app_user.id`（`MIN(id)`，即注册者）；`tenant.seat_used` = 该租户 `status=1` 的成员数；`seat_limit` 按套餐（FREE=3 / PRO=20 / ENTERPRISE=-1） | `WHERE owner_uid IS NULL` |
| 6 | `app_user.current_team_id` = 所属默认团队 id | `WHERE current_team_id IS NULL` |
| 7 | 为 `superadmin`（`tenant_id=0`）补登 `user_role(PLATFORM/SUPER_ADMIN)`，并建一个 identity | 同 1/4 |

> ⚠️ **播种字典必须用逐条 `insertIfMissing`，不能用"全表非空即跳过"**。本项目已踩过这个坑：`DataSeeder.seedSysConfig` 用"表非空则整体跳过"，导致老库永远拿不到新增配置项，后来不得不另写 `seedChartKeywordsV3` 补救。`permission`（~90 行）、`role`（13 行）、`role_permission`（~500 行）字典必须逐条按 `code`/`uk` 判定后插入，使后续版本新增权限点能自动补齐到已运行的库。

## 13. 分阶段实施计划

| 阶段 | 交付物 | 工期估算 | 验收标准 |
| --- | --- | --- | --- |
| **P0 地基**（不改变现有行为） | `AccessContext` + 兼容门面；JWT 扩展 claims；`SchemaMigration V2026_09_rbac_org`；14 张新表 DDL；`permission`/`role`/`role_permission` 字典播种；identity 与默认团队回填；`login_session` + 真 `logout` | 3~4 天 | 老用户登录、问数、建指标、驾驶舱全部行为与升级前一致；`schema_migration` 新增一行；无任何 403 回归 |
| **P1 后端权限**（服务端先行） | `@RequiresPermission` 四注解 + `PermissionAspect`；`PermissionService` 与四级缓存；`pv`/`sid` 吊销；`SecurityConfig` 域规则与 `hasAnyRole`；`GET /api/auth/permissions`；fail-closed 域注解全覆盖（datasource/semantic/fewshot/chart-rule/config/admin）；`ApiPermissionRegistry` 扫描 | 4~5 天 | 非授权账号调用 fail-closed 域接口全部 403；矩阵页无未标注告警；移除成员后旧令牌 ≤1s 失效 |
| **P2 组织与团队** | `module/org` 全部 Service/Controller；成员 CRUD、角色分配（含防提权）、团队树、自定义角色；`DataScopeInterceptor` + 资源表 `team_id`/`visibility`；`ResourceAclService` | 5~6 天 | 团队切换后指标/驾驶舱列表按范围收敛；降级 VIEWER 后写接口全部 403；存量资源可见性不变 |
| **P3 邀请机制** | `module/invite` 全部；四通道 + 状态机 + 席位原子占位 + 防提权；`NotifyService`（LOG 实现）；成员移除的资源/分享/邀请联动处置 | 4~5 天 | 并发 20 人接受 `seats=5` 的邀请，最终恰好 5 人入组、`seat_used=5`；被移除成员的公开分享链接立即 404 |
| **P4 前端权限** | `permission` store、`useMenus`、路由守卫升级、`v-perm`、`PermGuard`、`/403`、OrgSwitcher/TeamSwitcher、组织域五个新页 | 5~6 天 | VIEWER 登录看不到任何写按钮；菜单与后端权限码一致；切团队无脏数据残留 |
| **P5 运营与审计** | 平台四角色拆分；运营后台八个新页；`AuditService` 全事件接入；接口矩阵页；代客协助全链路 | 5~6 天 | OPERATOR 无法访问权限字典写接口；AUDITOR 全部写操作 403；ASSIST 令牌调用 `datasource:config:test` 被硬拒绝 |
| **P6 硬化与灰度** | 剩余域迁 fail-closed；`strict-domains` 逐域打开；SMTP/SMS 通知；审计归档任务；压测与渗透自查 | 3~4 天 | 全接口 fail-closed；权限校验性能达 §14.5 目标（缓存命中 P99 < 1ms） |

**并行与依赖**：P0 是全部后续阶段的前置；P1 与 P4 可部分并行（前端先按约定接口 mock）；P2 与 P3 强依赖 P1；P5 依赖 P1+P2。

**上线顺序**：先 P0 单独上线观察 1~2 天（纯地基、零行为变化，风险最低），再 P1+P4 同时上线（前后端权限必须同步，否则会出现"前端隐藏了但后端还能调"或反之），然后 P2→P3→P5→P6。

### 14.5 性能

| 指标 | 目标 |
| --- | --- |
| 权限校验开销（缓存命中） | P99 < 1ms，不产生 DB 查询 |
| 权限校验开销（缓存未命中） | P99 < 20ms（两次索引查询 + 集合运算） |
| `GET /api/auth/permissions` | P99 < 50ms |
| 数据范围改写对列表接口的影响 | P99 增量 < 5ms |
